## 共有オブジェクト

データファイルとアセットは共有オブジェクトです。一度だけ書き、上書きせず、いくつのバージョンから到達してもかまいません。Git の blob と同じです。バージョンからは次のように到達します。

| オブジェクト | パス | バージョンから到達するとき |
| --- | --- | --- |
| データファイル | `<data_dir><schema>/<table>/ducklake-<uuid>.parquet` | カタログが参照している |
| アセット | `assets/<sha256>` | `dataset.json` で `asset` の印を付けた列がどれかの行でその sha256 を持っている、または `tree.json` が並べている |

- 書き手は、バージョンを作る前に共有オブジェクトを置いてよい。バージョンから到達するまで、読み手には見えない
- 書き手は、既にあるオブジェクトをアップロードし直さなくてよい。ただしバージョンを書く前に消されることがあるので、バージョンから到達するオブジェクトが無い push は断る（[書く](/ja/spec/writing#push-が断られるとき)）

### データファイル

- 名前は DuckLake の付け方のまま。削除ファイルも同じ場所に置く
- 小さなファイルをまとめること（`ducklake_merge_adjacent_files`）はいつでもしてよい。新しいファイルを書き、何も消さない

### アセット

- 中身の sha256 を小文字の 16 進で名前にするので、同じ中身は 1 回だけ置く（[バージョン](/ja/spec/versions#アセット)）

## 共有オブジェクトを消してよいとき

次の 2 つがどちらも成り立つときだけです。

1. 有効なバージョン（`expired.json` の無いもの）のどれからも到達しない
2. 置かれてから猶予期間が過ぎている。猶予期間は、書き手が置いたものの、まだバージョンにしていないオブジェクトを守る

共有オブジェクトは、パスが上の表の形をしたファイルだけです。データディレクトリの下の `ducklake-<名前>.parquet` か、`assets/` に続く小文字 16 進 64 桁です。共有オブジェクトを消す処理は、それ以外のファイルを消してはいけません。

バージョンのカタログは、`ducklake.snapshot_id` の時点だけでなく、残しているすべてのスナップショットのデータファイルを名指しします。そのため、`files.json` の `tables` にあるファイルが到達するファイルのすべてではありません。カタログを開けない処理は `files.json` の `named` を使います。`files.json` が無いか、`named` の無い `files.json` を持つ有効なバージョンがあるときは、そのカタログを開くか、データファイルを消しません。

DuckLake 自身の片付け（`ducklake_cleanup_old_files`、`ducklake_expire_snapshots`）は 1 つのカタログしか見ないので、リポジトリから消すのに使ってはいけません。消すのは、リポジトリ全体を見る処理の役目です。

## 保持期間を過ぎたとき

バージョンの保持期間は、次の順に終わらせます。

1. `versions/<ID>/expired.json` を置く
2. バージョンのカタログ（`ducklake.duckdb` と `catalogs/`）と `files.json`・`tree.json` を消す
3. 猶予期間のあと、上の条件に合う共有オブジェクトを消す

```json expired.json
{ "expired_at": "2026-12-01T00:00:00Z", "reason": "retention" }
```

- `version.json` は残す。履歴にはそのバージョンがあったことと中身が残り、親のつながりも切れない
- `expired.json` を見た読み手は、`reason` が何であれ、保持期間を過ぎたものとして扱い、カタログを開かない
- ref が指すバージョンの保持期間を終わらせてはいけない

## 取り下げ

取り下げは、間違って公開した個人情報のように、公開してはいけないデータを消すための手順です。保持期間と違い、そのデータを持つバージョンを、有効なものも含めてすべて対象にし、猶予期間を待ちません。

1. そのデータを除いた新しいバージョンを作り、該当するバージョンを指しているブランチをすべてそこへ動かす。新しいバージョンの親はいまのバージョンなので、前へ動かすことになる。カタログは名指しするすべてのファイルに到達するので、新しいバージョンのカタログにはそのデータを持つスナップショットを残さない（作業カタログで `ducklake_expire_snapshots` を実行する）
2. 該当するバージョンを指すタグを消す
3. 個人情報を持つデータファイルや、それが写ったスクリーンショットなど、そのデータを持つ共有オブジェクトをすぐに消す。該当するバージョンから到達し、残すバージョンのどれからも到達しないものが対象。そのオブジェクトに到達するバージョンは、すべて該当するバージョンになる。該当するバージョンに保持期間を過ぎたものがあると、カタログが無いので、それがどのオブジェクトに到達していたかが分からない。その場合は、有効なバージョンのどれからも到達しない共有オブジェクトもすべてすぐに消す
4. 該当するバージョンそれぞれに `"reason": "withdrawn"` の `expired.json` を置き、カタログを消す

共有オブジェクトをカタログより先に消すのは、途中で止まった取り下げをやり直せるようにするためです。カタログが残っていれば、どのファイルがそのデータを持つかが分かります。

```json expired.json
{ "expired_at": "2026-12-01T00:00:00Z", "reason": "withdrawn" }
```

- `version.json` は、保持期間のときと同じく残す。記録そのもの（`message` や `inputs`）にそのデータがあれば記録も消し、履歴にはその位置で親が欠けて見える
- ミラーは自分の写しを持っている。`"reason": "withdrawn"` の `expired.json` を写したミラーは、元が消したカタログと共有オブジェクトを消す。元のホストはこれを強制できないので、知っているミラーに伝える
