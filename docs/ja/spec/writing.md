## 作業カタログ

書き手は作業カタログに書きます。リポジトリの外にある、SQLite の DuckLake カタログです。手元のパソコンでもホストのコンテナでも、作業カタログは 1 種類です。

- `DATA_INLINING_ROW_LIMIT 0` で ATTACH し、すべての行をデータファイルに書かなければならない
- データパスはリポジトリのデータフォルダ（`<root><data_dir>`）。新しいデータファイルはリポジトリに書かれる。HTTP 越しのリポジトリだけは例外で、新しいデータファイルは書き手のマシンのフォルダに書き、push がそれを上げる（[HTTP での push](/ja/spec/http#書き方)）
- `ducklake_expire_snapshots` と `ducklake_cleanup_old_files` を流してはいけない

## 段階

| 段階 | すること |
| --- | --- |
| チェックアウト | ブランチのバージョンのカタログから作業カタログを作り、そのバージョンを覚える。最初のバージョンの前は空のものを作る |
| コミット | 作業カタログの最後のスナップショットを新しいバージョンに固める。親は覚えておいたバージョン。中身を `dataset.json` で説明する |
| profile | テーブルごとに profile を測る（任意）。データファイルと列が親と同じテーブルは親の profile を引き継いでよい |
| push | データファイルを確かめ、カタログ、`dataset.json`・`files.json`・`tree.json`・profile、`version.json` の順にアップロードし、条件付きで ref を動かす |

書き手は、Git が `git push` までコミットを手元に置くのと同じく、コミットしたバージョンを手元に置いてあとで push してかまいません。push までリポジトリは変わりません。例外は作業カタログがリポジトリに書いたデータファイルで、どのバージョンもまだ参照していないので、push しないままなら猶予期間のあとに削除されます。

チェックアウトでは、DuckLake の管理用の表を、固めたカタログから SQLite へそのまま写します。固めるときはその逆で、最後のスナップショットまでの行を残します。どちらもデータファイルは書き換えません。

固めるとき、書き手は次のことをしなければなりません。

- 行をカタログの中に持つ作業カタログを断る
- 固めたカタログの `data_path` を `<root><data_dir>` の絶対 URL にする
- 絶対パスで記録されたデータファイルや、`data_dir` の外のデータファイルがあれば断る

## 変更がないとき

書き手は、親と同じ中身のバージョンを作らないようにするべきです。Git が親と同じ tree のコミットを作らないのと同じです。次のどちらかなら、親と同じ中身です。

- 最後のスナップショットが親のもの（`ducklake.snapshot_id`）と同じ
- 同じ表とビューがあり、どの表も列の名前と型が同じで、行が同じ（重複を数え、順番は問わない）。さらに `dataset.json` と `tree.json` の sha256 が親と同じ（どちらのバージョンにも `tree.json` が無いときを含む）

同じ入力から作り直した表は新しいデータファイルに書かれるので、ファイルやカタログのバイトを比べても判定できません。書き手はまずファイルを比べ、ファイルが違う表だけ行を読みます。行を読めないときはバージョンを作ります。頼まれたときは、`git commit --allow-empty` と同じく、変更がなくても作ってかまいません。

## 元に戻す

前のバージョンが持っていたものに戻す書き手は、`git revert` が新しいコミットを作るのと同じく、新しいバージョンを作ります。ブランチを後ろに動かしません。ブランチは既定では前にしか進まず（[ref](/ja/spec/refs)）、読む人が間のバージョンをすでに使っていることがあるためです。

新しいバージョンの親は、作業カタログをチェックアウトしたバージョンです。ほかのコミットと同じく、その後にブランチが動いていれば push は断られます。テーブルとビューは前のバージョンのスナップショットの時点と同じ列・同じ行を持ち、`dataset.json` と `tree.json` は前のバージョンのものです。作業カタログは新しいスナップショットでその状態にします。前のバージョンに無いテーブルは消し、その後に変わったテーブルは前のスナップショットの時点の行から書き直します。前のスナップショットがカタログに残っている必要があります。

## ブランチ

ブランチは、あるバージョンに `refs/heads/<名前>` を作ると作れます（[ref](/ja/spec/refs)）。ブランチでの作業も、`main` と同じくチェックアウト・commit・push で行います。ブランチのバージョンは、マージするまで `main` の履歴に入りません。

## マージ

マージは、別のブランチでの変更を、書いているブランチに取り込みます。書き手は次の 3 つのバージョンから結果を作ります。

- 自分側: 書いているブランチで、作業カタログをチェックアウトしたバージョン
- 相手側: 別のブランチのバージョン
- 基点: 自分側と相手側に共通の祖先のうち、ほかの共通の祖先がどれもその子孫にならないもの。`parents` はすべての要素をたどる。該当するものが 2 つ以上あるとき、書き手はマージを断る

基点が相手側なら、取り込むものはありません。基点が自分側なら、新しいバージョンを作らずにブランチを相手側へ動かします。それ以外では、書き手はマージのバージョンを作ります。その `parents` は自分側、相手側の順で、ほかの commit と同じく、ブランチがその後に動いていれば push は断られます。基点のカタログとそのスナップショットが残っている必要があり、保持期間を過ぎた基点からはマージを断ります。

### テーブル

2 つのバージョンで `schema.table` が同じテーブルを、同じテーブルとみなします。テーブルごとに 3 つのバージョンを比べます。列とその型、行（重複を数え、順番は問わない）が同じなら、2 つのバージョンは同じテーブルを持っています。

| 自分側と相手側（基点との比較） | マージのバージョンが持つもの |
| --- | --- |
| どちらも変えていない、または両方が同じように変えた | そのテーブル |
| 片方だけが変えた、追加した、または削除した | その側のテーブル。削除したならテーブルは無い |
| 片方が削除し、もう片方が変えた | 衝突 |
| 両方が違うように変えた、または違うものを追加した | 下の主キーでの行のマージ、または衝突 |

ビューは SQL で比べ、主キーの無いテーブルと同じに扱います。

### 主キーでの行のマージ

同じテーブルへの 2 つの変更は、自分側と相手側が `dataset.json` でそのテーブルに同じ `primary_key` を宣言し、基点も同じものを宣言している（または基点にそのテーブルが無い）とき、行ごとにマージします。列とその型は自分側と相手側で同じでなければなりません。両方で列が変わったテーブルは衝突です。

行は主キーの値で識別し、キーごとに上のテーブルと同じように比べます。片方だけが追加・変更・削除した行はその側の変更を取り込み、両方が違うように変えたキーは衝突です。3 つのバージョンのどれかで、キーに `NULL` を持つ行か、同じキーが 2 回以上現れるテーブルは衝突です。

主キーの無いテーブルは、2 つの側が違う行を変えていても行ごとにはマージしません。書き手は、主キーの無いテーブルについて警告してかまいません。マージのために作ったキー（行番号など）は主キーではありません。どの行が同じ行かを表さないためです。

### 説明

`dataset.json` と `tree.json` はキーごとにマージします。オブジェクトはメンバーごとに比べ、`tables` の要素は `schema` と `name`、`fields` の要素は `name` で対応を取ります。ほかの値（文字列・数・リスト）は丸ごと扱います。片方だけが変えたならその側の値、両方が違うように変えたなら衝突です。`tree.json` のファイルはパスで対応を取ります。

カタログから作る値（`rows`、各列の `type` と `nullable`）はマージせず、マージのバージョンのカタログから作り直します。

### 衝突

衝突が 1 つでもあれば、マージはバージョンを作りません。書き手は衝突をテーブルごとに、行なら主キーの値とともに並べ、リポジトリは何も変えません。マージする人は、衝突しないようにどちらかのブランチを変えてから、もう一度マージします。

### マージのバージョン

作業カタログは自分側からチェックアウトし、新しいスナップショットで結果を持ちます。データファイルは新しく書いてもよく、相手側から丸ごと取り込むテーブルなら相手側と同じファイルを参照してもかまいません。`diff` は、マージのバージョンを最初の親である自分側と比べます。

## 書き込みの順番

1. データファイル・アセット
2. `versions/<ID>/ducklake.duckdb`（と `catalogs/`）
3. `versions/<ID>/dataset.json`・`versions/<ID>/files.json`・`versions/<ID>/tree.json`・`versions/<ID>/profiles/`
4. `versions/<ID>/version.json`
5. ref（条件付き）

途中で止まった書き手は、読み手に見えるものを何も変えていません。残ったファイルはどの ref からも参照されず、その中のデータファイルは猶予期間のあとに消されます。

バージョンのファイルは一度だけ書きます。既に同じ中身のファイルがあれば先へ進み、違う中身なら止まります。

## push が断られるとき

古い作業カタログからの push は、次の 2 つの確認で断られます。

1. 新しいバージョンが、いまブランチが指すバージョンの子孫でない。ほかの人が先に push した
2. カタログが参照するデータファイルか、`tree.json` が並べるファイルがリポジトリに無い。ホストは行が持つアセットも確認してよい。有効なバージョンから猶予期間より長く参照されなかったファイルは、書き手が見つけたあとでも消されていることがある

どちらの場合も、書き手はチェックアウトし直し、作業をやり直して、もう一度 push します。1 つめの場合は、代わりにブランチを自分の作業にマージしてもかまいません。リポジトリを片付ける必要はありません。断られたバージョンはどの ref からも参照されていません。
